# Чек-лист перед публикацией

Короткий список для каждого релиза, PR и любой публикации (issue, релиз, docs).
Приложение открытое (GPLv3), поэтому «закрыть код» — не цель. Защищаем то, что
даёт доступ: ключ подписи, токены, инфраструктуру и данные пользователей.

## Никогда не публиковать

- `app/tarn-release.keystore`, `*.jks`, `local.properties` (там `KEYSTORE_PASS`,
  `ALIAS_NAME`, `ALIAS_PASS`), `service-account-credentials.json`;
- `*.har`, `*.log`, `logcat`, скриншоты и видео с профилями, UUID, ключами,
  ссылками подписок или IP серверов — в HAR и логах часто остаются заголовки
  `Authorization`/`Cookie`;
- реальные `vless://`/`vmess://`/`ss://` ссылки, subscription-URL, IP и имена
  ваших серверов, ключи TLS серверной части;
- персональные данные: email, телефоны, идентификаторы устройств, имена
  пользователей из отчётов.

Правило простое: если файл даёт доступ — он не попадает в репозиторий, в PR,
в issue и в ассеты релиза.

## Перед релизом

1. `gitleaks detect --redact` по обоим репозиториям (app и core), включая историю.
2. Проверить, что в диффе нет новых `.har`, `.log`, `.keystore`, `local.properties`.
3. Release notes: без IP/UUID/провайдеров; примеры — только плейсхолдеры.
4. Собрать APK с `--rerun-tasks`, приложить `SHA256SUMS` и `tarn-version-metadata.json`.
5. Проверить установку поверх предыдущего релиза на устройстве.
6. Core: тег `tarnvpn-v<version>` указывает на коммит, из которого собран AAR
   (GPL-оферта в README должна вести на существующий тег).

## Безопасность CI

- Секреты — только в GitHub Secrets; в workflow нет ключей и паролей в тексте.
- `permissions: contents: read` по умолчанию; расширять точечно на job.
- Не использовать `pull_request_target` с секретами: PR из форков получает код
  атакующего с доступом к ним.
- Actions — по возможности пиннить по SHA, а не по плавающему тегу.
- Сборка релиза подписью — только в окружении с ручным подтверждением
  (protected environment), не на каждый PR.

## Если секрет всё же утёк

1. Считать его скомпрометированным и **отозвать** (токен GitHub, пароль, ключ).
   Удаление коммита не отменяет утечку — история и форки уже содержат его.
2. Для ключа подписи: перевыпуск невозможен «прозрачно» — публикуется
   предупреждение, новая подпись и инструкция удалить/переустановить приложение.
3. Для токенов: отозвать, выпустить новый fine-grained с минимальными правами.
4. Записать инцидент в release notes, если он касался пользователей.
